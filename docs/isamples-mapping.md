# iSamples Core 2.0 as a third `/service` read format

Status: **implemented**. `GET /service/samples` and `GET /service/samples/:igsn` (ADR [0042](adr/0042-format-negotiation-on-the-service-api.md)) emit an iSamples Core 2.0 record when the caller's `Accept` header asks for one, alongside the default IGSN Sample Core record (`docs/igsn-core-mapping.md`), the DataCite 4.7 record (`docs/datacite-mapping.md`) and the OGC-OMS / SOSA record ([`docs/oms-mapping.md`](oms-mapping.md)).

Source: `Mapping_implementation_IGSN-Core_v0.10.0_v-Finale.docx`, section 4 (`mapCoreToISamples`), crosswalks 1.1, 1.3, 1.4 and the masking rule in section 5.

The mapping lives in `packages/domain/src/sample/isamples/`, pure and I/O-free:

- `isamples-schema.ts`: `iSamplesSampleSchema` / `ISamplesSample`, `ISAMPLES_MEDIA_TYPE`, `ISAMPLES_SCHEMA_URI` and the three vocabulary constants.
- `to-isamples-sample.ts` (`toISamplesSample`): the top-level assembly.
- `to-isamples-agents.ts`: `toISamplesAgent` (one agent, one role) and `toISamplesAgents` (the role picker, run once per target list).
- `to-isamples-categories.ts`: the material and sampled-feature crosswalks (§1.3, §1.4) and the constant object type, built by the concept builder.
- `to-isamples-sampling-event.ts`: `produced_by` (site, coordinates, masking, elevation string).

**Core is the pivot mapped, never `Sample`.** `toISamplesSample` takes a `CoreSample`, so the call is `toISamplesSample(toCoreSample(sample, frontendUrl))`. `toCoreSample` (`packages/domain/src/sample/core/to-core-sample.ts`) stays the single place converting a `Sample` to Core; an iSamples deviation never reopens it.

## Media type

- `application/vnd.otelo.isamples+json` on the two `/service` GET routes.
- A Core record (`application/json`) is the default: an `Accept` of `application/json`, `application/*`, `*/*` or no header at all serves Core.
- An unserved `Accept` answers `406`.
- `POST` and `PUT` ignore `Accept` and always answer an IGSN Core record, the format switch being a read concern.
- Both GET routes publish `Accept` as a documented header parameter, so `/service/docs` offers all three formats and `/service/openapi.json` carries a schema for each.

## Sensitive-location masking

`rightsAndAccess.sensitiveLocation` drives `produced_by.sample_location.obfuscated`:

- `obfuscated` mirrors the flag.
- `true` also drops `latitude` and `longitude`.
- `elevation` and the `sampling_site` place names stay, since the contract masks the horizontal coordinates alone.

## Agent and IdentifiedConcept shape

`toISamplesAgent(agentRole, role)` builds one Agent from one `CoreAgentRole` and one of its roles: `name` <- `joinContactName(firstname, lastname)` or the organization name; `pid` <- `agent.id` when set; `affiliation` <- affiliation names joined with `", "` when any (one string in iSamples); `role` <- the §1.1 crosswalk, an exhaustive `Record<CoreRole, string>` (`Creator -> collector`, `Collector -> collector`, `ChiefScientist -> chiefScientist`, `Researcher -> researcher`, `Curator -> curator`, `Registrant -> registrant`, `HostingInstitution -> hostingInstitution`, `ProjectManager -> projectManager`, `ProjectMember -> projectMember`, `DataManager -> dataManager`; see ADR [0046](adr/0046-additional-scientific-roles.md)). It takes the role as its own argument because a Core agent may carry several roles at once while iSamples emits one agent per role. `ProjectManager`, `ProjectMember` and `DataManager` stay unused today, same as `HostingInstitution`: no target list in `to-isamples-sample.ts` currently picks them.

`toISamplesAgents(responsibility, wanted)` walks every `AgentRole`, keeps the roles in `wanted`, and calls `toISamplesAgent` once per kept role, in Core order. It is the single picker behind `registrant`, `produced_by.responsibility`, `produced_by.authorized_by` and `curation.responsibility`.

IdentifiedConcept shape for the three iSamples vocabularies, built by `to-isamples-categories.ts`'s concept builder: `pid` <- `<vocabulary base><slug>`, `label`, `scheme_name`, `scheme_uri`, with bases `https://w3id.org/isample/vocabulary/material/` (scheme `.../1.0/materialsvocabulary`, "iSamples Materials Vocabulary"), `.../sampledfeature/` (scheme `.../1.0/sampledfeaturevocabulary`, "iSamples Sampled Feature Type vocabulary"), `.../materialsampleobjecttype/` (scheme `.../1.0/materialsampleobjecttype`, "iSamples Material Sample Object Type Vocabulary"). The material crosswalk is a local `MaterialHead` union with a five-key `Record`; an `it.each` tripwire over `MATERIAL_TREE.rock_and_sediment.choices` fails the suite as soon as a sixth head (liquid, gas) joins the material tree, until it is added to the crosswalk.

A round-trip-style guard (`to-isamples-sample.spec.ts`) lists every Core path as projected or deliberately dropped, so a new Core field fails the suite until it is placed in one list or the other.

## Deviations from the contract document

- `sample_identifier` <- `identification.landingPage`, the schema's "URI identifying the sample": the contract has no row for it.
- `sample_location` sits on `produced_by`, not `produced_by.sampling_site` as the contract writes, because the 2.0 `SamplingSite` schema forbids that key (`site_location` is its own slot and stays unused).
- `curation.label`, `.access_constraints` and `.curation_location` are our reading of the contract's `curation.*` rows.
- A non-point geometry (a track or an area) emits no coordinates (`ponytail:` centroid note in the code, add one if an integrator needs it).
- `label` and `dc_rights` read `[0]` of an array Core fixes at exactly one element (`identification.titles`, `rightsAndAccess.rightsURIs`); a related resource's `label` reads `[0]` of `targetTitles` the same way.
- `toISamplesAgent` takes the role as an explicit second argument, since a Core agent may hold several roles at once while iSamples emits one agent per role.
- `keywords[]` carries no `pid`, since our economic-interest concepts have no URI.
